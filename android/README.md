# Payables Tracker Android SMS Sync

## Goal

A native Android companion app that forwards only bank transaction SMS messages (debits and credits) to the existing Payables Tracker SMS capture pipeline. The web app remains the source of truth for parsing, account mapping, duplicate detection, review, and Cash Book posting.

## Current backend contract

The existing Supabase Edge Function is deployed as `sms-capture` and accepts capture requests at:

`POST https://magxbczgrxeypryjborr.supabase.co/functions/v1/sms-capture/capture`

Headers:

- `Authorization: Bearer <user-generated capture token>`
- `Content-Type: application/json`

Body:

```json
{
  "sender": "bank sender id",
  "message": "original SMS body"
}
```

The token is a capture token generated by the signed-in Payables Tracker user in the existing SMS Capture page. The function hashes and validates the token; the Android app must never embed a Supabase service-role key, anon/publishable key as a secret, or another user's token.

## Android app responsibilities

1. Provide a clear onboarding screen explaining exactly which SMS content is processed and why.
2. Let the user connect with a capture token generated from their own signed-in Payables Tracker account.
3. Store the token encrypted using Android Keystore-backed encryption.
4. Capture incoming SMS only after explicit user consent and only when the app is authorized to use the relevant Android SMS capability.
5. Filter locally for likely bank transaction alerts (debit, credit, UPI, card, transfer, refund, deposit, withdrawal). Do not upload unrelated personal SMS.
6. Preserve multipart SMS body assembly and sender metadata.
7. Queue eligible messages locally and forward them with WorkManager when network connectivity is available.
8. Use bounded exponential retry for transient failures; do not retry permanent 4xx failures indefinitely.
9. Record delivery state without logging raw SMS bodies or capture tokens.
10. Provide pause/resume, disconnect/revoke guidance, last sync time, queued count, and failed count.

## Existing backend behaviour to preserve

- The Edge Function validates the per-user capture token.
- It parses amount, direction, date, account identifier, reference and description.
- It performs account mapping and duplicate checks.
- It creates a Cash Book movement only when its existing validation permits it.
- Uncertain or invalid messages remain in SMS Review.
- The Android app must not create Cash Book rows directly or implement a second parser/posting pipeline.

## Security and privacy requirements

- TLS only.
- Android Keystore-backed token encryption.
- No token or SMS body in Logcat, analytics, crash reports, or notifications.
- Do not request contacts, call log, location, or unrelated permissions.
- Do not scan historical inbox messages in the first release; capture new incoming messages only.
- Keep only the minimum local queue payload needed for retry and delete it after confirmed delivery.
- Do not send messages from non-bank senders or non-transaction content.
- Provide an in-app privacy disclosure and link to the published privacy policy before enabling capture.
- A user can pause capture and disconnect at any time.
- Use a unique message id/hash for local queue idempotency; server-side duplicate detection remains authoritative.

## Google Play distribution gate

SMS permissions are restricted. The current Google Play policy requires the app to qualify for a permitted use or an approved exception; the SMS-based money-management use case (for example, budgeting/transaction tracking) is listed as an exception subject to Google Play review and approval. Do not assume approval.

Before publishing:
- Submit the SMS permissions declaration and explain that transaction SMS capture is essential to the app's money-management functionality.
- Provide a prominent in-app disclosure and consent flow.
- Publish an accurate privacy policy and Data safety declaration.
- Demonstrate that only financial transaction messages are processed and that unrelated SMS content is not collected or shared.
- If Google Play rejects the requested permission, do not attempt to bypass policy through notification access or another API to derive SMS content. Reassess the product distribution and compliant alternatives.

Official policy: https://support.google.com/googleplay/android-developer/answer/17225965
Android default-handler guidance: https://developer.android.com/guide/topics/permissions/default-handlers

## Delivery milestones

1. **Foundation:** native project, onboarding, connection configuration, secure token storage.
2. **Capture:** permission eligibility/flow, incoming SMS receiver, bank-transaction-only local filter, multipart support.
3. **Delivery:** persistent queue, WorkManager retry, API client, delivery diagnostics.
4. **Quality:** parser/API contract tests, duplicate/retry/offline tests, permission denial and revocation tests.
5. **Release readiness:** privacy policy, Data safety answers, Play Console declaration, signed AAB, internal testing track.
6. **Production rollout:** only after Play review approval and user opt-in. No changes to the existing web production deployment are required for the initial Android client.

## Non-goals for v1

- Replacing the user's default SMS app.
- Reading historical SMS inbox content.
- Sending or deleting SMS.
- Reading OTPs or non-financial conversations.
- Automatically approving or rejecting SMS Review records.
- Writing transactions directly to Cash Book.
